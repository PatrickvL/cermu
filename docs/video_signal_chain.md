# Video Signal Chain Emulation — Future Work

## Problem Statement

cermu currently maps color indices directly to RGBA pixels via a palette lookup
table (LUT).  This produces "correct" colors under the assumption that someone
has already solved the analog→digital conversion and chosen values that look
right on a modern LED/LCD/OLED display.

In reality, each emulated system has a multi-stage signal chain between the
video chip's color output and what the user saw on a physical screen.  None of
this chain is currently modeled.

## Physical Signal Chain

```
  Color Index / Luma+Chroma
       │
       ▼
  ┌──────────────────────┐
  │ Video Chip Output    │  Digital → analog conversion
  │  (VIC-II: luma+chroma composite; NES PPU: NTSC composite waveform;
  │   Spectrum ULA: TTL RGB with 0xCD/0xFF levels)
  └──────────┬───────────┘
             │
       ▼  (on-board circuitry)
  ┌──────────────────────┐
  │ Signal Conditioning  │  Amplifiers, filters, impedance matching,
  │                      │  RF modulator (if present), S-Video separator
  └──────────┬───────────┘
             │
       ▼  (connector + cable)
  ┌──────────────────────┐
  │ Cable / Connector    │  RCA composite, DIN, RF, S-Video, SCART RGB
  │                      │  Each carries different signal quality / bandwidth
  └──────────┬───────────┘
             │
       ▼
  ┌──────────────────────┐
  │ Display Decoder      │  NTSC/PAL chroma decoder (comb filter, delay line,
  │                      │  or simple 1-line decoder), color burst phase lock
  └──────────┬───────────┘
             │
       ▼
  ┌──────────────────────┐
  │ CRT Phosphor / Gun   │  Beam intensity → phosphor excitation
  │                      │  Gaussian spot profile, bloom, phosphor persistence,
  │                      │  shadow mask / aperture grille geometry
  └──────────────────────┘
```

## Per-System Signal Characteristics

### C64 (VIC-II / MOS 6569 / 6567)

- **Output**: Composite video (luma + chroma on single wire), S-Video on later models.
- **Color generation**: The VIC-II generates luma and chroma as analog voltage
  levels.  Colors are phase angles on the NTSC/PAL color subcarrier.  The
  actual RGB you see depends entirely on the decoder (TV) interpreting the
  composite signal.
- **Implication**: There is no "true" VIC-II palette.  Every C64 looked
  slightly different depending on the monitor, cable quality, chroma decoder
  accuracy, and even VIC-II chip revision (luma levels differ between 6567 R5,
  6567 R8, 6569 R1, 6569 R3, 6569 R5).
- **Future work**: Model luma/chroma levels per VIC-II revision → composite
  signal → selectable decoder model → RGB.

### NES (RP2C02 / RP2C07)

- **Output**: The PPU generates NTSC composite video *directly* — there is no
  RGB stage at all.  The 64-color master palette does not exist in silicon; it
  is a human-decoded approximation.
- **Color generation**: Each of the 64 palette entries is a specific phase
  angle and amplitude on the composite waveform, generated by a simple counter
  and comparator.  The emphasis bits attenuate specific channels.
- **Implication**: The "base 64-color table" is inherently an approximation.
  Different captures from different PPU revisions and TVs yield different
  tables.  This is why multiple community palettes exist (FBX, Wavebeam,
  Nestopia, etc.) — they are all valid decodes.
- **Future work**: Model the 2C02 composite waveform generator → apply
  NTSC decoding → RGB.  This would make emphasis and greyscale bit-accurate
  rather than LUT-approximated.

### ZX Spectrum (Ferranti ULA)

- **Output**: TTL-level RGB (active-high, directly driving the display).
  BRIGHT flag increases voltage level.  Simple, no chroma encoding.
- **Color generation**: 3-bit RGB (8 colors) × bright bit = 15 unique colors.
  The voltage levels are fixed by the ULA design.
- **Implication**: Least analog ambiguity — but the CRT's interpretation of
  the voltage levels and the phosphor characteristics still matter.
- **Future work**: Model the exact voltage→luminance curve and phosphor color
  temperature.

## Stages to Model (Priority Order)

### Stage 1: CRT Simulation (Post-Process Shader)

Applicable to all systems.  A GPU post-process that simulates:

- **Scanlines**: Visible gaps between raster lines (intensity modulated).
- **Phosphor mask**: Shadow mask or aperture grille dot pattern.
- **Bloom / glow**: Bright pixels bleed into neighbors.
- **Color temperature**: Warm (CRT) vs. cool (modern LCD).
- **Curvature**: Barrel distortion of a curved CRT face.

This is visual-only, doesn't affect emulation accuracy, and is the most
impactful quality-of-life improvement for authenticity.

### Stage 2: Composite Artifact Modeling

Most impactful for **NES** and **C64** (both output composite).  Models:

- **Chroma bleed**: Adjacent colors leak into each other through the
  composite signal's limited bandwidth.
- **Dot crawl**: Phase interference between luma and chroma.
- **NTSC artifacts**: Color fringing that NES games deliberately exploit
  (e.g., additional "colors" from alternating pixel patterns).

This changes the actual rendered pixels and should be optional (toggle-able).

### Stage 3: Per-Revision Analog Modeling

Models the actual voltage/phase values per chip revision:

- VIC-II luma tables per revision (6567 R5/R8, 6569 R1/R3/R5).
- NES PPU composite waveform generator per revision (RP2C02G, RP2C07).
- Generates palettes from first principles rather than hand-tuned tables.

### Stage 4: Cable and Connector Modeling

Models signal degradation per connection type:

- RF: Significant high-frequency loss, ghosting.
- Composite RCA: Moderate bandwidth, standard chroma artifacts.
- S-Video: Separated luma/chroma, cleaner image.
- RGB (SCART, direct): No chroma artifacts, closest to "ideal".

## Relationship to Current Palette System

The current `NamedPalette` infrastructure (user-selectable palette tables per
video chip) serves as the **Stage 0** solution: pre-computed end-result tables
that approximate what different sources measured or preferred.  This is the
right approach for now and will remain useful even after signal-chain modeling
is implemented, because:

1. Users who want maximum performance (no shader overhead) can use palette LUTs.
2. Pre-computed tables serve as validation targets for the signal chain model.
3. Community palettes capture aesthetic preferences that pure physics modeling
   may not reproduce (e.g., "how I remember my childhood TV looking").

The `VideoChipBase::select_palette()` / `NamedPalette` API naturally extends
to signal-chain-generated palettes — they're just another palette source.
